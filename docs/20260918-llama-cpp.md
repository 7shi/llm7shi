# llama.cpp Endpoint Support: Four Fixes and a Prefix

This document covers a cluster of issues found while exercising `openai.py` against a real llama.cpp server (`llama-server`), and the `llama.cpp:` vendor prefix added once they were fixed.

## Background

Earlier work ([20260112-api-key-security.md](20260112-api-key-security.md)) established `api_key=""` as the secure default for custom endpoints reached via `base_url`, and ([20260903-responses-api.md](20260903-responses-api.md)) established `base_url is None` as the signal for "real OpenAI, route to the Responses API." Both assumptions were tested against a llama.cpp server running a reasoning-capable GGUF model (`Ternary-Bonsai-2-27B-PQ2_0`) and found to have drifted or been incomplete.

## The `openai` SDK Now Rejects an Empty `api_key`

**Problem**: The installed `openai` package (3.7.0) raises `OpenAIError: Missing credentials` when `api_key=""` is passed, even though the empty string was chosen specifically so no `Authorization` header would be sent. The SDK's `_enforce_credentials` check treats an empty string as absent rather than as "deliberately no key."

**Solution**: Both places that constructed a keyless client (`base_url` given without `api_key_env`, and `api_key_env` given but its environment variable unset/empty) now pass a non-empty placeholder (`"not-needed"`) instead of `""`. The placeholder is never a real credential and llama-server ignores the `Authorization` header entirely, so this doesn't reopen the leakage risk the empty string was preventing — it just satisfies the SDK's new non-empty check.

## `delta.reasoning_content`, Not `delta.reasoning`

**Problem**: [20260607-openrouter-reasoning.md](20260607-openrouter-reasoning.md) documented `delta.reasoning` as the field OpenAI-compatible providers use for streamed thinking. llama.cpp (and vLLM) instead populate `delta.reasoning_content` — confirmed by inspecting raw SSE chunks (`reasoning_content` deltas) and the OpenAI SDK's parsed `ChoiceDelta` objects. `process_chunk()` only checked `delta.reasoning`, so llama.cpp's thinking content was silently dropped from every response instead of erroring, making the gap easy to miss.

**Solution**: `process_chunk()` now checks `delta.reasoning or delta.reasoning_content`. Tests mocking `delta` with `MagicMock()` needed `reasoning_content` set explicitly to `None` alongside the existing `reasoning = None`, since an unset `MagicMock` attribute is truthy by default and would otherwise fake a nonexistent reasoning field.

## `OPENAI_BASE_URL` Bypassed the Destination-Based Routing Rule

**Problem**: The Responses-vs-Chat-Completions routing rule from [20260903-responses-api.md](20260903-responses-api.md) checks the local `base_url` variable (populated only by the `model@base_url` string syntax) for `None`. But `OpenAI()` independently resolves an unset `base_url` argument from the `OPENAI_BASE_URL` environment variable. So pointing a compatible server at the library purely via that env var — without using `@` in the model string — left the local `base_url` at `None`, misclassifying the destination as real OpenAI and routing to the Responses API, which llama.cpp doesn't implement. This only went unnoticed in manual testing because the llama.cpp build in use happened to also expose a `/v1/responses` endpoint; a server without one would fail outright.

**Solution**: `effective_base_url = base_url or os.environ.get("OPENAI_BASE_URL")` is computed once at the top of `generate_content()` and used for both the client-construction branch and the transport routing check, so the two can't disagree about where the request is actually going.

## `llama.cpp:` Vendor Prefix

**Problem**: Pointing at a local llama-server still required the full `model@http://host:port/v1` syntax, or the `OPENAI_BASE_URL` environment variable, for every call — more ceremony than the common case (a server on the default `localhost:8080`) warranted.

**Solution**: A `llama.cpp:` prefix was added to `compat.py`, e.g. `llama.cpp:my-model`. Unlike `OPENAI_COMPATIBLE_VENDORS` (`openrouter:`, `groq:`, `grok:`, `cerebras:`), it needed two departures from that dict-driven mechanism: no `api_key_env` (llama-server takes no key), and the default `base_url` (`http://localhost:8080/v1`) only applies when `OPENAI_BASE_URL` is *also* unset — otherwise the vendor default would silently override an endpoint the user had already configured via the env var this same investigation just wired into the routing decision. It's therefore its own `elif` branch rather than a new dict entry. An empty model name (`llama.cpp:`) gets a display-only placeholder (`"local"`), since llama-server ignores the model name in the request anyway.

This reverses part of the "Not Implemented (By Design)" stance in [20260112-api-key-security.md](20260112-api-key-security.md), which had deliberately avoided inferring `base_url` for core vendors like `ollama:`. The difference here is that llama.cpp already has a de facto standard default port (`8080`, unlike Ollama's non-OpenAI-compatible native API on `11434`), and the prefix's `base_url` is skipped entirely — not silently overridden — whenever the user has configured one another way.

## What Stayed As-Is: the gpt-oss Template Filter

A related question came up but wasn't acted on: since llama.cpp now parses gpt-oss's `<|channel|>`/`<|message|>` control tokens into `reasoning_content` itself on recent builds, is the client-side `GptOssTemplateFilter` (see `llm7shi/openai.md`) still needed? It was kept: the filter only activates on the exact opt-in model string `"llama.cpp/gpt-oss"`, and a deployment that pins an older llama.cpp build (or another server that still emits raw control tokens) would still need it. The explicit opt-in trigger means keeping it costs nothing for users who don't set that model string.

## Testing

All four fixes and the new prefix have regression tests: `tests/test_gpt_oss.py` (`reasoning_content` extraction, `OPENAI_BASE_URL`-only routing) and `tests/test_compat_vendor.py::TestLlamaCppPrefix` (default URL, env-var precedence, explicit `@` override, empty-model placeholder). See [openai.md](../llm7shi/openai.md) and [compat.md](../llm7shi/compat.md) for the module-level rationale.
