# Usage Class

## Why This Design

### Provider-Agnostic Token Usage
**Problem**: Every provider reports token usage differently - not just different field names (`prompt_eval_count` vs `input_tokens` vs `prompt_tokens`), but different structures (flat on the chunk vs nested under a `usage`/`usage_metadata` object) and different delivery timing (only on the final chunk, repeated cumulatively on every chunk, or as a distinguishable extra chunk that must be opted into). See `docs/20260915-token-usage.md` for the full survey. Forcing these into one rigid schema would mean either dropping provider-specific detail (reasoning tokens, cache hits, cost) or inventing a lowest-common-denominator shape nobody's raw response actually has.

**Solution**: `Usage.raw` keeps the provider's own dict untouched - no renamed keys, no dropped fields - so nothing is lost. Each provider's `extract_usage()` builds `raw` by dumping the provider's own usage object wholesale (`.model_dump()`) rather than hand-picking keys, so a field a provider adds later shows up automatically without a code change here. Ollama is the one exception: it has no separate usage sub-object, so its usage fields sit on the same chunk as `message`/`model`/timing fields; `extract_usage()` dumps the whole chunk and excludes the known non-usage keys instead, keeping the same forward-compatibility property.

On top of `raw`, `Usage` exposes best-effort normalized properties (`input_tokens`, `output_tokens`, `reasoning_tokens`, `cached_tokens`, `total_tokens`) for the dimensions that generalize across providers well enough to be worth a common name. Each one is computed by checking the provider-specific keys it could be under and returns `None` when a provider simply doesn't report that dimension (e.g. Ollama has no per-call reasoning-token count - its thinking and answer tokens are bundled into one `eval_count` with no way to split them back out) rather than fabricating a value. `to_dict()` returns just these normalized fields (omitting the `None` ones) for callers who want a clean, comparable summary without `raw`'s provider-specific noise.

### Aggregating Usage Across Calls
**Problem**: A caller tracking usage over a batch or session needs to sum multiple `Usage` objects, but `raw`'s shape is provider-specific (nested `*_details` dicts, provider-only fields like OpenRouter's `cost`) - summing it field-by-field either has to special-case each provider's nesting or silently drops fields that don't line up between calls, and the result stops being a faithful "raw provider response" for any single call anyway.

**Solution**: `Usage.__add__` (`+`) sums only the normalized fields and ignores `raw` entirely - the result's `raw` holds just those summed fields, keyed by their normalized names (`input_tokens`, `output_tokens`, etc.), not a merged provider-shaped dict. Because `input_tokens`/`output_tokens`/`total_tokens` already check for their own normalized name first, and `reasoning_tokens`/`cached_tokens` were extended to do the same, a summed `Usage` reads back correctly through its own properties - so `(a + b) + c` chains without special-casing the second addition. A field missing from both operands stays absent from the result (not fabricated as 0); a field present on either side sums with the other treated as 0.
